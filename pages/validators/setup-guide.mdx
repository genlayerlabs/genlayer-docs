# Setting Up Your GenLayer Validator

Running a GenLayer Validator node ensures the security and reliability of the GenLayer network. Below are the requirements for running a GenLayer validator.

Registration creates a validator identity; it does not by itself make the node an active validator. Check the deployed self-stake minimum, activation epoch and priming requirements separately. During epoch 0, a registered and healthy node may correctly be waiting for activation.

For a deeper understanding of how staking works in GenLayer, see the [Staking documentation](/understand-genlayer-protocol/core-concepts/optimistic-democracy/staking).

## System Requirements

| Resource | Requirement |
|----------|-------------|
| **Memory** | 16 GB RAM |
| **CPU** | 8-core (AMD64 only) |
| **Disk** | 128 GB SSD/NVMe |
| **Network** | 100 Mbps |
| **OS** | 64-bit Linux |
| **Software** | Docker, Python 3.10+ (`python3` on `PATH`, with pip and venv) |

GPU not required unless running LLMs locally. See [detailed requirements](/validators/system-requirements) for more info.

## Create the Validator Wallet

Before setting up your validator node, you need to create your validator wallet and stake GEN tokens.

### Understanding Validator Addresses

<Callout type="info">
GenLayer validators use three distinct addresses:

| Address | Description | Where Used |
|---------|-------------|------------|
| **Owner** | The only address that can withdraw staked funds. Keep this secure (cold wallet). | CLI wizard - signs staking transaction |
| **Operator** | Hot wallet on your server that signs blocks. Can be same as owner, but separate is recommended. | Node config: `operatorAddress` |
| **Validator Wallet** | Smart contract created when you join. This is your validator's on-chain identity. | Node config: `validatorWalletAddress` |

The wizard outputs all three addresses at the end. Save them - you'll need the Validator Wallet and Operator addresses for your node configuration.

**Back up the owner wallet's private key or seed phrase.** The wizard's keystore export only covers the operator key — the owner key never touches your server and cannot be recovered from the node. If it is lost, staked funds can no longer be exited or claimed. See [Owner, Operator, and ValidatorWallet](/understand-genlayer-protocol/core-concepts/optimistic-democracy/staking#owner-operator-and-validatorwallet) for how the three relate.
</Callout>

### Prerequisites

- **Node.js** (v20 or higher; Node.js 22 for a fresh installation)
- **GenLayer CLI** - Install the release candidate (`rc` tag), the v0.40 line for Bradbury Phase 2. The default npm tag (`latest`) still selects an older release:
  ```bash copy
  npm install -g genlayer@rc
  genlayer --version
  ```
- **GEN tokens** - Read the deployed self-stake minimum with `genlayer staking epoch-info --network testnet-bradbury`, and keep additional GEN for gas. **42,000 GEN is a protocol default, not a guaranteed current network setting.** Delegation does not replace required self-stake.

During the public DNS cutover, first verify the network identity described on the [networks page](/developers/networks). If you have an assigned provider endpoint, add `--rpc "$BRADBURY_RPC_URL"` to each CLI command below. Do not continue against an endpoint returning the previous network genesis.

### Using the Validator Wizard

The easiest way to create your validator wallet is using the interactive wizard:

```bash copy
genlayer staking wizard --network testnet-bradbury
```

The wizard guides you through:

1. **Account setup** - Create or select your owner account
2. **Network selection** - Choose testnet-bradbury
3. **Funding source** - Stake from your wallet or from a vesting contract
4. **Balance verification** - Checks your balance against the deployed minimum and gas requirement
5. **Operator setup** - Create and export an operator keystore for your validator server
6. **Stake amount** - Enter how much GEN to self-stake using the current on-chain minimum
7. **Validator creation** - Submits the staking transaction
8. **Identity setup** - Set your validator's public profile (moniker, website, etc.); skip it with `--skip-identity`
9. **Summary** - Shows the owner, operator and validator wallet addresses

<Callout type="info">
  **Save Your Validator Wallet Address!** After the wizard completes, note down your **Validator Wallet** address. You'll need this for your node configuration.
</Callout>

<Callout type="warning">
  Phase 2 registration requires the operator public key and a proof of possession bound to the owner, chain and validator-wallet factory. Use an operator account available to the qualified CLI so it can sign the proof. An external operator address alone is not sufficient; do not use the old `validatorJoin(address)` flow.
</Callout>

#### Operator Keystore Export

The wizard creates and exports an operator keystore file for you to transfer to your validator server. If your server is compromised, your staked funds (controlled by owner) remain safe.

### Verify Your Validator

After completing the wizard, verify your status:

```bash copy
genlayer staking validator-info 0xYourValidatorWallet... --network testnet-bradbury
# Includes registered validators that are not active yet:
genlayer staking validators --network testnet-bradbury
```

### Managing Your Validator

```bash copy
# Add more stake
genlayer staking validator-deposit 0xYourValidatorWallet... --amount 1000gen --network testnet-bradbury

# Check active validators
genlayer staking active-validators --network testnet-bradbury

# Exit (initiates 7-epoch unbonding)
genlayer staking validator-exit 0xYourValidatorWallet... --shares 100 --network testnet-bradbury

# Claim after unbonding period
genlayer staking validator-claim 0xYourValidatorWallet... --network testnet-bradbury

# Update identity
genlayer staking set-identity 0x... --moniker "New Name" --network testnet-bradbury
```

## Set Up the Validator Node

Once your validator wallet is created and staked, set up your node software.

### Dependencies

#### LLM Access

Each validator needs access to a Large Language Model (LLM) for executing and evaluating Intelligent Contracts.

It is up to each validator to select the model they want to use.

Possible options:

- Run an open-source model locally on the same machine with a GPU
- Run an open-source model on a different machine
- Connect to a hosted inference provider (OpenAI, Anthropic, Heurist, Atoma network etc.)

See the [GenVM Configuration](/validators/genvm-configuration) page for partner credits, provider setup, and the greybox fallback strategy.

#### GenLayer Chain RPC access

Each validator needs HTTP and WebSocket access to the GenLayer Chain to read state, send transactions and subscribe to chain updates. For Bradbury Phase 2:

- HTTP: `https://rpc.testnet-chain.genlayer.com`
- WebSocket: `wss://rpc.testnet-chain.genlayer.com` (API key required)

An endpoint of the previous Bradbury chain is incompatible even when it returns the same chain ID.

Create a key at [app.conduit.xyz/rpc-keys](https://app.conduit.xyz/rpc-keys). The WebSocket requires a key; anonymous HTTP access does not prove that WebSocket subscriptions will work. Set it in the node's environment:

```sh copy
export GENLAYERNODE_ROLLUP_GENLAYERCHAINRPCKEY="<your Conduit API key>"
```

With Docker, add the same variable to the private `.env` file next to `docker-compose.yaml`. The node sends it as `X-AccessKey`. Never put it in the RPC or WebSocket URLs, or anywhere in `config.yaml`.

One full node can be shared between multiple validators. The optimal validator-to-node ratio is currently under evaluation.

### Setup

#### Download the node software

1. Select the version of the node you want to run by checking the available builds

   You can use this command to list available versions:

   ```sh copy
   curl -s "https://storage.googleapis.com/storage/v1/b/gh-af/o?prefix=genlayer-node/bin/amd64" | grep -o '"name": *"[^"]*"' | sed -n 's/.*\/\(v[^/]*\)\/.*/\1/p' | sed 's/-rc/~rc/' | sort -ruV | sed 's/~rc/-rc/' | awk '{c=$0; sub(/-rc\..*/,"",c)} /-rc\./{if (c in s) next} !/-rc\./{s[c]=1} {split(c,p,"."); l=p[1]"."p[2]} !m{m=l} l==m{print}' | head -n 5
   ```

   You should see a list like this

   ```sh
   v0.6.0-rc.2
   v0.6.0-rc.1
   ```

   Typically, you will want to run the latest version **approved for Bradbury Phase 2**, not an arbitrary `latest` tag. The list above is a documentation example generated from changelog entries; an entry can precede artifact publication. Confirm the exact version in the release announcement and check all download URLs before installation. Do not fall back to an older release when a target artifact returns 404.

2. Download the packaged application
   ```sh copy
   export version=v0.6.0-rc.2 # example target; confirm it is published and approved before use
   base=https://storage.googleapis.com/gh-af/genlayer-node/bin/amd64/${version}
   curl -fI "${base}/genlayer-node-linux-amd64-${version}.tar.gz"
   curl -fI "${base}/genlayer-node_${version}_SHA256SUMS"
   curl -fI "${base}/genlayer-node_${version}_SHA256SUMS.sigstore.json"
   # Stop if any check fails; only download after all three succeed.
   wget "${base}/genlayer-node-linux-amd64-${version}.tar.gz"
   ```
3. Verify the download (v0.6.0 and later)

   Each release from v0.6.0 on publishes a signed checksum file next to the tarball. Verify it before you extract: extraction feeds the GenVM setup script, so a tampered tarball must be caught here. You need [cosign](https://docs.sigstore.dev/cosign/system_config/installation/).

   ```sh copy
   base=https://storage.googleapis.com/gh-af/genlayer-node/bin/amd64/${version}
   wget ${base}/genlayer-node_${version}_SHA256SUMS ${base}/genlayer-node_${version}_SHA256SUMS.sigstore.json

   # 1. The checksum file was produced by GenLayer's release workflow.
   cosign verify-blob \
     --bundle "genlayer-node_${version}_SHA256SUMS.sigstore.json" \
     --certificate-identity-regexp '^https://github\.com/genlayerlabs/genlayer-node/\.github/workflows/release-package\.yml@' \
     --certificate-oidc-issuer https://token.actions.githubusercontent.com \
     "genlayer-node_${version}_SHA256SUMS"

   # 2. The tarball matches the checksum file.
   sha256sum -c "genlayer-node_${version}_SHA256SUMS" --ignore-missing
   ```

   If either command fails, do not extract: delete the download and fetch it again. Releases before v0.6.0 have no checksum file.

   The same releases also publish `install.sh`, covered by the same checksum file. After verifying, `./install.sh --install-dir /opt/genlayer-node/${version} --tarball genlayer-node-linux-amd64-${version}.tar.gz` replaces steps 4 and 5.

4. Extract the node software

   The tarball has one top-level directory, `genlayer-node-linux-amd64/`; `--strip-components=1` puts its contents straight into `./${version}`.

   ```sh copy
   mkdir -p ${version}
   tar -xzf genlayer-node-linux-amd64-${version}.tar.gz -C ./${version} --strip-components=1
   cd ./${version}
   ```

5. Run the GenVM setup

   This step needs Python 3.10 or newer, available as `python3` on your `PATH`, with `pip` and `venv` (on Debian/Ubuntu: `python3-pip` and `python3-venv`). Check with `python3 --version`.

   Run it in the final install location: it writes this directory's absolute path into the GenVM binaries. If you move the installation later, run it again there.

   ```sh copy
   python3 ./opt/genvm/v0.6.0-rc10/bin/setup.py # v0.6.0-rc.1 ships GenVM v0.6.0-rc10: check with `ls opt/genvm`
   ```
It does following:

- Downloads missing runners if any
- Verifies runners hashes
- Sets `elf`/`mach-o` interpreter for all binaries (modules, genvm)
- Rust precompilation for built-in runners

### Configuration

Before you can start up the node, you need to configure it.

#### `config.yaml`

This is the main configuration file of your node. Without it, your node won't start

The file needs to be located at `configs/node/config.yaml`

You can use the following example configuration. **Note:** For most users, you will only need to replace the `rollup` and `consensus` sections with the values for your target network (see [Network-Specific Consensus Configuration](#network-specific-consensus-configuration) below).

Set `genvm.root_dir` to the GenVM directory the release ships. v0.6.0-rc.1 ships `opt/genvm/v0.6.0-rc10`, but its config template says `./opt/genvm/v0.6.0-rc1`: set `genvm.root_dir: ./opt/genvm/v0.6.0-rc10` (check with `ls opt/genvm`). `install.sh` writes the right value for you.

```yaml copy
# rollup configuration
rollup:
  genlayerchainrpcurl: "TODO: Set your GenLayer Chain HTTP RPC URL here" # GenLayer Chain RPC URL
  genlayerchainwebsocketurl: "TODO: Set your GenLayer Chain WebSocket RPC URL here" # GenLayer Chain WebSocket URL
  # An API key of the RPC provider never goes in these URLs or in this file:
  # set it in the environment as GENLAYERNODE_ROLLUP_GENLAYERCHAINRPCKEY.
  # The node sends it in this header (default X-AccessKey):
  # genlayerchainrpckeyheader: "X-AccessKey"
  provider: "TODO: Set your GenLayer Chain provider" # Rollup operator name; surfaces as the "provider" label on RPC-driven metrics. Set explicitly per deployment.
# consensus contracts configuration
consensus:
  # The deployment-specific fields are empty: take them from your network's documentation.
  consensusaddress: "" # AddressManager contract address for this deployment.
  manifestpath: "configs/node/protocol-manifest.json" # Trusted producer protocol manifest for this deployment: save your network's manifest (from its documentation) at this path; a dev-env deploy places its own here too. Relative paths resolve against the node root. A mismatch with consensusaddress is refused at startup.
  chainid: "" # DECIMAL chain id this deployment was made on (not hex, no leading zeros). Held independently of the manifest so a manifest describing another deployment is caught.
  # genesis: 47930 # (Optional) Genesis block number for this consensus deployment. If not provided, it will be auto-detected by searching for the first log from the ConsensusMain contract.
  # chain_submit_buffer: "30s" # (Optional) Slack reserved at the end of each consensus step to submit the resulting on-chain tx (commit vote, reveal vote, proposed receipt) before the slot closes. Tune to underlying settlement chain latency. Default 30s.
  # admissiontimeout: "15s" # (Optional) Bound on the startup deployment admission check. Never unbounded. Default 15s.
# data directory
datadir: "./data/node"
# logging configuration
logging:
  level: "INFO"
  # json: `true` for json output to console, false for human readable log formatting
  json: false
  # Configuration for https://github.com/natefinch/lumberjack
  file:
    # enabled: set to `true` to save logs to a folder
    enabled: true
    # The console and this file carry different levels on purpose: INFO to the
    # terminal, DEBUG here. That split is why the file sink exists — INFO is what
    # an operator watches live and has to stay readable, DEBUG is the complete
    # record kept for investigation. Set this to INFO and the two collapse: the
    # file becomes a copy of the console and stops being a record.
    #
    # It has to be on permanently. An incident is over by the time anyone could
    # raise the level, and the detail cannot be reconstructed after the fact.
    #
    # What it accepts: every debug line lands on disk, including RPC and GenVM
    # payloads chosen by the caller. The level bounds nothing —
    # maxsize/maxage/maxbackups below are what limit the volume.
    level: "DEBUG"
    # folder: path to the folder where to store logs. Relative paths go under `datadir`.
    folder: logs
    # maxsize: maximum size in megabytes of the log file before it gets rotated.
    maxsize: 10
    # maxage: maximum number of days to retain old log files based on the timestamp encoded in their filename.
    maxage: 7
    # maxbackups: maximum number of old log files to retain. Set to 0 for no limit
    maxbackups: 100
    # localtime: determines if the time used for formatting the timestamps in backup files is the computer's local time. Set to `false` to use UTC time.
    localtime: false
    # compress: determines if the rotated log files should be compressed using gzip
    compress: true
# node configuration
node:
  # Uncomment if the ID of the node is different from the validator wallet address.
  # It is used to identify the node in the network.
  # id: "node"
  # Mode can be "validator" or "full".
  # Default value is "validator".
  mode: "validator"
  # Address of the ValidatorWallet contract (required for validator mode)
  validatorWalletAddress: ""
  # Address of the operator that performs consensus duties for the ValidatorWallet
  operatorAddress: ""
  admin:
    port: 9155
    # snapshot_dir: bounding directory for POST /snapshot write-to-path mode.
    # A caller-supplied destDir must resolve inside this directory, else the
    # request is rejected with 400. Relative paths go under `datadir`; an
    # absolute path is used as-is (e.g. to target a dedicated disk).
    # Default: snapshots  (i.e. <datadir>/snapshots)
    # snapshot_dir: snapshots
  rpc:
    # host: 0.0.0.0 # bind address for the HTTP listener (default: all interfaces)
    port: 9151 # RPC server port
    # allowed_origins: unified browser-origin allowlist applied to BOTH
    # the HTTP transport (CORS) and the WS upgrade (gorilla CheckOrigin).
    # Exact-match URLs only — no wildcard syntax beyond "*". Omit or
    # leave empty to keep the permissive default ["*"]. Operators can
    # override per-transport for WS via rpc.websocket.origins (rare).
    # allowed_origins:
    #   - "https://wallet.example.com"
    #   - "https://app.example.com"
    # websocket: inbound JSON-RPC WS endpoint for eth_subscribe /
    # zks_subscribe plus all non-subscribe passthrough. Omit this whole
    # block (the default) to keep WS disabled.
    #
    # When enabled, the default is single-listener mode: WS upgrades are
    # served on the existing RPC listener (port above) — one port, one
    # firewall entry, one reverse-proxy upstream. To run a dedicated WS
    # listener instead (Geth-conventional dual-port pattern), set `port`
    # to a value other than 0 and other than rpc.port (e.g. 9152) and
    # set `host` for that listener.
    # websocket:
    #   enabled: true
    #   # port: 0            # 0 or unset → single-listener on rpc.port (default)
    #   # host: 0.0.0.0      # only used in dual-listener mode
    #   path: "/ws"          # ws upgrade path — disambiguates HTTP RPC (POST /)
    #                        # from WS upgrade (GET /ws) at the URL level.
    #                        # Set to "/" for legacy behaviour (root path).
    #   origins:             # WS-only override of rpc.allowed_origins (rare;
    #                        # leave unset to inherit the unified allowlist)
    #     - "*"              # permissive default — tighten via rpc.allowed_origins
    #   max_conns: 1024
    #   max_conns_per_ip: 16
    #   max_subs_per_conn: 32
    #   outbox_size: 256     # per-connection bounded queue; full → connection dropped
    #   write_timeout: 10s
    #   ping_interval: 30s
    #   max_message_bytes: 10485760   # 10 MB cap on a single inbound frame (parity with rpc.max_request_body_bytes)
    # ratelimit_whitelist: IPs or CIDRs that bypass rate limiting entirely
    # ratelimit_whitelist:
    #   - "127.0.0.1"
    #   - "::1"              # IPv6 loopback (localhost on macOS)
    #   - "10.0.0.0/8"
    endpoints:
      # RPC method groups, keyed directly under `endpoints`. Each group toggles a
      # family of methods and may nest per-method overrides and rate limits.
      # Default rate limits (req/s per IP) apply even when unset:
      #   genlayer: 20, genlayer_debug: 2, ethereum: 50, zksync: 50
      #   gen_call: 2, gen_getContractSchema: 2 (method-level defaults)
      genlayer:
        enabled: true # gen_* methods
      # gen_dbg_* methods (trie dump, transaction trace). OFF by default: these
      # replay a transaction through GenVM and return internal execution output,
      # so they are debug tooling, not a public API. Enable deliberately, and
      # only on an RPC bind that untrusted callers cannot reach. Matches the
      # node's own code default and the go-ethereum debug-namespace convention.
      genlayer_debug:
        enabled: false # gen_dbg_* methods
      ethereum:
        enabled: true # eth_* proxy methods (eth_blockNumber, eth_call, ...)
      zksync:
        enabled: false # zks_* proxy methods (zks_getBlockDetails, ...)
        #
        # A group with no overrides may use the bool shorthand (`ethereum: true`).
        #
        # Custom per-group rate limit + per-method overrides (object form):
        #   genlayer:
        #     enabled: true
        #     ratelimit: 100              # 100 req/s per IP instead of the default 20
        #     methods:
        #       gen_call:
        #         enabled: true
        #         ratelimit: 5            # 5 req/s per IP instead of the default 2
        #       gen_getContractSchema:
        #         enabled: false          # disable a single method within an enabled group
        #
        # Proxy allowlist (opt-in): disable a proxy group, then re-enable only a
        # vetted set under its `methods`. Every other eth_*/zks_* is then rejected
        # with -32601 (method not found) and not forwarded upstream. Leave the
        # groups enabled (the default) to forward all eth_*/zks_* (passthrough).
        #   ethereum:
        #     enabled: false
        #     methods:
        #       eth_getBalance: true
        #       eth_getTransactionCount: true
        #       eth_getCode: true
        #       eth_getStorageAt: true
        #       eth_call: true
        #       eth_estimateGas: true
        #       eth_gasPrice: true
        #       eth_blockNumber: true
        #       eth_getBlockByHash: true
        #       eth_getBlockByNumber: true
        #       eth_getTransactionByHash: true
        #       eth_getTransactionReceipt: true
        #       eth_getLogs: true
        #       eth_chainId: true
        #       eth_syncing: true
        #       eth_accounts: true
        #       eth_sendRawTransaction: true   # write — enable only if clients submit raw txs
        #   zksync:
        #     enabled: false                   # zks_* left fully disabled (no vetted client use)
  ops:
    port: 9153 # Ops server port (/health, /metrics, /balance, /snapshot)
    endpoints:
      # Compatibility metadata. The current Ops server registers /metrics,
      # /health, /balance, and /snapshot regardless of these values. `doctor`
      # consults `health` to decide whether to run its HTTP health probe.
      metrics: true
      health: true
  # Execution-trace store and debug-trace reply bounds. All optional; the
  # values below are the built-in defaults. Uncomment to tune at runtime — no
  # rebuild needed.
  # trace:
  #   retention_blocks: 1000000       # keep traces this many blocks behind the tip (0 disables retention)
  #   max_trace_bytes: 33554432       # 32 MB: a single trace larger than this is never stored
  #   # Per-field cap on the public gen_dbg_traceTransaction reply. Each free-form
  #   # field (return_data, stdout, stderr, genvm_log) carries contract-emitted
  #   # output, so its size is contract-controlled. Over the cap, the field is
  #   # truncated and the cut is marked in-band. 0 takes the default.
  #   max_debug_field_bytes: 262144   # 256 KB per field
# genvm configuration
genvm:
  root_dir: ./opt/genvm/v0.6.0-rc10
  start_manager: true # if true node will start genvm manager itself
  manager_url: http://127.0.0.1:3999
  # Permits are charged PER EXECUTION by the genvm manager, and one
  # nondeterministic execution costs 8 of them (permits.nondet). This value is
  # therefore a permit budget, not an execution count: 32 admits 4 concurrent
  # nondet executions, which is what the previous `8` bought when a run cost 2
  # permits. Leaving it EMPTY is preferable — autodiscovery sizes it from the
  # host and already speaks this unit.
  permits: 32 # Leave empty for autodiscovery, put a number for updating genvm permits on startup
  # Same unit as `permits` above, but a sync execution costs 4 rather than 8,
  # so 256 admits the 64 concurrent replays the previous `64` bought at cost 1.
  sync_permits: 256 # Optional: permits used while significantly behind (bulk replay). Leave empty to reuse the steady-state `permits` value.
  # sync_permits_lag_threshold: blocks-behind above which the node runs the replay
  # budget (sync_permits) instead of the live budget (permits); at or below it the
  # node is treated as caught up. Keyed on the actual sync lag, not the health
  # gradient. Uncomment to tune; default 1000.
  # sync_permits_lag_threshold: 1000
  # sync_wait_timeout bounds the gen_* READ path — not GenVM execution: a read
  # (gen_call / gen_getContractState / gen_getContractCode /
  # gen_dbg_traceTransaction) waits up to this long for the node to sync the
  # requested block and index the record, then returns a not-synced error.
  sync_wait_timeout: "20s"
  # sync_wait_poll_interval is the re-check cadence those same reads use while they
  # poll for an artifact that lands just after its block is synced, bounded overall
```

#### Network-Specific Consensus Configuration

Replace the matching sections of your `config.yaml` with the block for the network you want to join. Replace each top-level section as a whole rather than adding a second `rollup:` or `consensus:` key.

Since v0.6, the node refuses to start unless `consensus.manifestpath` points at the trusted protocol manifest of the network. The release package contains no network files: download the manifest for your network from this page and save it at `configs/node/protocol-manifest.json`, the path `manifestpath` names. Relative paths resolve against the node root. At startup, the node also refuses a manifest whose registry does not match `consensus.consensusaddress`, or whose chain does not match `consensus.chainid`.

#### Overriding Configuration with Environment Variables

Any configuration value in `config.yaml` can be overridden using environment variables with the prefix `GENLAYERNODE_`. Only keys that exist in the file are picked up: a key that is commented out, such as `consensus.genesis` in the template, must be uncommented before its variable has an effect.

**Pattern:**

- Replace dots (`.`) with underscores (`_`)
- Convert to uppercase
- Add the `GENLAYERNODE_` prefix

**Examples:**

| Config Key | Environment Variable |
|------------|---------------------|
| `rollup.genlayerchainrpcurl` | `GENLAYERNODE_ROLLUP_GENLAYERCHAINRPCURL` |
| `rollup.genlayerchainwebsocketurl` | `GENLAYERNODE_ROLLUP_GENLAYERCHAINWEBSOCKETURL` |
| `consensus.consensusaddress` | `GENLAYERNODE_CONSENSUS_CONSENSUSADDRESS` |
| `consensus.chainid` | `GENLAYERNODE_CONSENSUS_CHAINID` |
| `consensus.manifestpath` | `GENLAYERNODE_CONSENSUS_MANIFESTPATH` |
| `consensus.genesis` | `GENLAYERNODE_CONSENSUS_GENESIS` |
| `node.mode` | `GENLAYERNODE_NODE_MODE` |
| `node.validatorWalletAddress` | `GENLAYERNODE_NODE_VALIDATORWALLETADDRESS` |
| `node.operatorAddress` | `GENLAYERNODE_NODE_OPERATORADDRESS` |
| `node.rpc.port` | `GENLAYERNODE_NODE_RPC_PORT` |
| `logging.level` | `GENLAYERNODE_LOGGING_LEVEL` |

These have no key in `config.yaml` and are read from the environment only:

| Variable | Purpose |
|----------|---------|
| `GENLAYERNODE_PASSWORD` | Keystore password. Use it instead of `--password`, which is visible in process listings and shell history. |
| `GENLAYERNODE_CONFIG_PATH` | Path to the config file (default `configs/node/config.yaml`). |
| `GENLAYERNODE_ROLLUP_GENLAYERCHAINRPCKEY` | API key of the chain RPC provider. Never put it in the endpoint URLs. |
| `GENLAYERNODE_NODE_OPERATOR_TOKEN` | Bearer token for the ops server's `POST /snapshot` route. Without it the route refuses every caller. Generate one with `openssl rand -hex 32`. |

**Usage example:**

```sh copy
# Override the RPC port
export GENLAYERNODE_NODE_RPC_PORT="9151"

# Set validator wallet address
export GENLAYERNODE_NODE_VALIDATORWALLETADDRESS="0x..."

# Set logging level
export GENLAYERNODE_LOGGING_LEVEL="DEBUG"
```

Environment variables take precedence over values in `config.yaml`, making them ideal for Docker deployments or sensitive values you don't want in configuration files.

#### Import the Operator Key

The operator key is used by your node to sign blocks and perform validator duties.

The account commands read the node's keystore password from `GENLAYERNODE_PASSWORD`. Set it once per shell, without echoing it. Do not pass it with `--password`: command-line arguments can be visible in process listings and shell history.

```sh copy
read -rsp "Keystore password: " GENLAYERNODE_PASSWORD
export GENLAYERNODE_PASSWORD
printf '\n'
```

#### Option 1: Import from CLI Wizard (Recommended)

The wizard exports an encrypted Web3/geth-compatible operator keystore. Transfer
only that file to the validator server. With the default `datadir: ./data/node`
and `node.keystoredir: keystore`, install it as the node service user:

```bash copy
install -d -m 700 ./data/node/keystore
test ! -e ./data/node/keystore/operator.json || exit 1
install -m 600 /path/to/operator-keystore.json ./data/node/keystore/operator.json
```

Set `GENLAYERNODE_PASSWORD` privately to the **export passphrase**. This preserves
the file's encryption; it does not re-encrypt it with a different password. Adjust
the destination if your configured data or keystore path differs. Set the public
`node.operatorAddress` and `node.validatorWalletAddress` in your config and run
doctor to verify unlocking and registration. The current `account import` command
requires an export passphrase argument; it does not prompt for it. The encrypted
file installation above avoids putting that secret in process arguments.

#### Option 2: Generate New Operator Key

You can also generate a new operator key directly on the server:

```sh copy
./bin/genlayernode account new -c $(pwd)/configs/node/config.yaml --setup
```

For Phase 2 registration, the CLI also needs that operator account to sign its proof of possession. Securely export/import the operator keystore into the owner-side CLI and select it in the wizard; providing the address alone is insufficient. Never transfer the owner key to the server.

#### Restoring Your Operator Key

Stop the old node before transferring its operator to another server. Restore the
encrypted keystore using the procedure above, retain its passphrase privately and
verify the public address against registration before startup. Never run both
nodes with the same operator simultaneously.

#### Backing Up Your Operator Key

Back up the encrypted operator keystore, public config and trusted manifest using
your approved secure backup location. Keep the passphrase separately. Preserve
owner-only permissions and test recovery before discarding the source. Do not
print or export the raw private key as part of routine installation.

### Running the node

Once you have configured everything, you are ready to start the node.

<Callout type="warning" emoji="🚨">
    **Important:** Before starting the node, ensure you have:
    1. **Operator key** imported into the node (see "Import the Operator Key" above)
    2. **Validator wallet address** - obtained after joining as validator via `genlayer staking wizard` or `validator-join`

    Set `node.mode: validator` explicitly and require doctor to pass. Do not assume an incomplete validator configuration will safely become a full node.
</Callout>

#### Running the Node using the binary

1.  Set the LLM Provider API Key

    Set the environment variable of at least one LLM provider. See the [GenVM Configuration](/validators/genvm-configuration) page for details on LLM providers and obtaining API credits.

    ```sh copy
    # Read by the default GenVM LLM config
    export HEURISTKEY='your_heurist_api_key'
    export ANTHROPICKEY='your_anthropic_api_key'
    export OPENAIKEY='your_openai_api_key'
    export XAIKEY='your_xai_api_key'
    export GEMINIKEY='your_gemini_api_key'

    # Read only by the release LLM config (genvm-modules-llm-release.yaml, used by greyboxing)
    export OPENROUTERKEY='your_openrouter_api_key'
    export COMPUT3KEY='your_comput3_api_key'
    export IOINTELLIGENCEKEY='your_ionet_api_key'
    export MORPHEUS_API_KEY='your_morpheus_api_key'
    export LIBERTAI_API_KEY='your_libertai_api_key'
    ```

2.  Run the WebDriver container

    ```sh copy
    docker compose up -d # Starts the WebDriver needed by the GenVM web module
    ```

    In v0.6.0-rc.1 every `docker compose` command fails while `NODE_PASSWORD` is empty, also for the WebDriver alone. For a binary node, set any non-empty value in the `.env` next to `docker-compose.yaml`.

    The node starts the GenVM manager and its modules itself (`genvm.start_manager: true` in the config template).

    **WebDriver resource metrics (optional).** To report the WebDriver container's CPU, memory and traffic as `genlayer_node_*{component="webdriver"}` series, also start the read-only Docker API proxy, and give only the node process `DOCKER_HOST=tcp://127.0.0.1:2375` (see step 4):

    ```sh copy
    docker compose up -d docker-socket-proxy
    ```

    Run the node as a user that is not in the `docker` group, and do not `export DOCKER_HOST` in a shell you also use for `docker` commands: they would reach the read-only proxy and fail. Without `DOCKER_HOST` the node skips these metrics.

3. Checking Your Configuration

    Run `doctor` before the first start, from the install directory, with the same environment the node will run with:

    ```sh copy
    ./bin/genlayernode doctor
    ```

    It checks, in order:
    - GenLayer Chain connectivity
    - the consensus deployment: it reads the on-chain contracts and checks them against the trusted protocol manifest at `consensus.manifestpath`
    - the GenVM configuration: binaries, module config, the LLM provider keys and a live call to each enabled provider, and the WebDriver

4.  Run the node

    With `GENLAYERNODE_PASSWORD` set (see [Import the Operator Key](#import-the-operator-key)):

    ```sh copy
    ./bin/genlayernode run -c $(pwd)/configs/node/config.yaml
    ```

    With WebDriver resource metrics:

    ```sh copy
    DOCKER_HOST=tcp://127.0.0.1:2375 ./bin/genlayernode run -c $(pwd)/configs/node/config.yaml
    ```

<Callout type="info">
  If you are running the node via SSH, the process might terminate if your
  connection drops. To prevent this, consider using a terminal multiplexer like
  `screen` or `tmux` to keep the node running in the background even if your SSH
  session ends. You can find a guide on using `screen`
  [here](https://www.networkworld.com/article/967925/how-the-linux-screen-tool-can-save-your-tasks-and-your-sanity-if-ssh-is-interrupted.html).
</Callout>

#### Running the Node using docker-compose

You can also run the GenLayer node using Docker and Docker Compose. Release candidate images (`v0.6.0-rc.N`) are published for `linux/amd64` only; stable images also cover `linux/arm64`.

Before the first start, in the directory with your `docker-compose.yaml`:

- `configs/node/config.yaml` holds your network's `rollup` and `consensus` values (see [Configuration](#configuration)).
- `configs/node/protocol-manifest.json` is your network's trusted manifest (see [Network-Specific Consensus Configuration](#network-specific-consensus-configuration)). The v0.6.0-rc.1 compose file does not mount it: add a `docker-compose.override.yml` next to `docker-compose.yaml`, which Docker Compose reads automatically:

  ```yaml copy
  services:
    genlayer-node:
      volumes:
        - ./configs/node/protocol-manifest.json:/app/configs/node/protocol-manifest.json:ro
        # Only if you customize the LLM config (for example for greyboxing):
        # - ./genvm-module-llm.yaml:/app/opt/genvm/v0.6.0-rc10/config/genvm-module-llm.yaml:ro
  ```
- The node container runs as uid `10001`, and the bind-mounted `./data` keeps its host owner. Let that user write to it once:

  ```sh copy
  mkdir -p ./data && sudo chown -R 10001:10001 ./data
  ```

1. Create a `docker-compose.yaml` file with the following content:

```yaml copy
# A fixed project name: the container names below are fixed too, so a stack
# started from a new release directory must be the SAME Compose project, or
# Docker refuses with "container name ... is already in use". With it, `up -d`
# from the new version's directory recreates the old version's containers.
name: genlayer-node
services:
  webdriver-container:
    container_name: genlayer-node-webdriver
    image: yeagerai/genlayer-genvm-webdriver:0.0.12
    shm_size: 2gb
    security_opt:
      - no-new-privileges:true
    environment:
      PORT: 4444
      HEALTHCHECK_AUTO_RESTART: "${HEALTHCHECK_AUTO_RESTART:-true}"
    ports:
      - "${WEBDRIVER_PORT:-4444}:4444"
    restart: unless-stopped
    labels:
      com.genlayer.health-recovery.logs: "true"
      com.genlayer.network: "${NETWORK_NAME:-unknown}"
    healthcheck:
      test:
        - CMD-SHELL
        - |
          set -eu
          boot=$$(awk '{print $$22}' /proc/1/stat)
          if curl -fsS --max-time 10 "http://localhost:$${PORT:-4444}/healthcheck?mode=text&url=https%3A%2F%2Ftest-server.genlayer.com%2Fstatic%2Fgenvm%2Fhello.html"; then
            printf '%s 0\n' "$$boot" > /tmp/webdriver-health-failures
            exit 0
          fi
          age=$$(awk -v ticks="$$boot" -v hz="$$(getconf CLK_TCK)" '{print int($$1-ticks/hz)}' /proc/uptime)
          [ "$$age" -ge 10 ] || exit 1
          read -r previous failures 2>/dev/null < /tmp/webdriver-health-failures || failures=0
          [ "$${previous:-}" = "$$boot" ] || failures=0
          failures=$$((failures + 1))
          printf '%s %s\n' "$$boot" "$$failures" > /tmp/webdriver-health-failures
          if [ "$$failures" -ge 4 ] && [ "$${HEALTHCHECK_AUTO_RESTART:-true}" != false ]; then
            printf 'Container webdriver (%s) found to be unhealthy - Restarting container now\n' "$$(cat /etc/hostname)" > /proc/1/fd/1
            children=$$(cat /proc/1/task/1/children)
            for child in $$children; do kill -KILL "$$child"; done
          fi
          exit 1
      interval: 30s
      timeout: 12s
      retries: 4
      start_period: 10s
  # docker-socket-proxy — read-only Docker API gateway for the node's WebDriver
  # resource stats and Alloy's recovery-log reader. Runs with the `node` OR
  # `monitoring` profile, so it comes up alongside
  # a node container AND alongside a monitoring/telemetry bring-up — the latter is
  # how a binary/systemd node (node not containerized) gets its webdriver metrics.
  #
  # The node and Alloy use this read-only gateway instead of the host socket.
  #   Reading container stats requires the Docker API. Previously the node reached
  #   the host /var/run/docker.sock directly (bind-mounted into the container, or via
  #   docker-group membership for a binary node) — but that grants the FULL Docker
  #   API as root (a `:ro` flag does NOT restrict API calls), so a node compromise
  #   could escalate to host root. This proxy REPLACES the node's socket access,
  #   restricted to read-only container endpoints (CONTAINERS=1;
  #   POST=0 => it returns 403 for create / exec / image operations).
  #   Health checks stop only their own service process; recovery has no Docker API access.
  #     - Published ONLY on 127.0.0.1:2375 (host loopback), never 0.0.0.0: 2375 is
  #       the unauthenticated Docker API, so it must not leave the host. A container
  #       node reaches it over the compose network (tcp://docker-socket-proxy:2375);
  #       a binary/systemd node reaches it on the host (tcp://127.0.0.1:2375).
  #     - Standard, widely-audited image (tecnativa/docker-socket-proxy).
  #
  # The node points DOCKER_HOST at this proxy and NEVER falls back to the host
  # socket: if DOCKER_HOST is unset the node skips webdriver metrics entirely
  # (non-fatal). Note those are the webdriver container's CPU/memory/traffic series
  # (genlayer_node_*{component="webdriver"}) that feed validator resource dashboards —
  # so keep DOCKER_HOST set to keep those panels populated. Disabling metrics
  # permits removing the node's DOCKER_HOST; Alloy still needs this gateway.
  docker-socket-proxy:
    image: tecnativa/docker-socket-proxy:v0.5.0
    container_name: genlayer-node-docker-proxy
    environment:
      CONTAINERS: 1 # GET /containers/{json,inspect,stats} — read-only via POST=0
      VERSION: 1 # required by the Docker client's API-version negotiation
      NETWORKS: 1 # read-only network metadata required by Alloy Docker discovery
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock:ro
    ports:
      # Loopback ONLY (never 0.0.0.0) — 2375 is the unauthenticated Docker API and
      # must not be exposed beyond the host. Lets a binary/systemd node reach the
      # proxy at tcp://127.0.0.1:2375; container nodes use the service name instead.
      - "127.0.0.1:2375:2375"
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://localhost:2375/version"]
      interval: 10s
      timeout: 3s
      retries: 5
      start_period: 5s
    security_opt:
      - no-new-privileges:true
    restart: unless-stopped
    profiles:
      - node
      - monitoring
  genlayer-node:
    image: yeagerai/genlayer-node:${NODE_VERSION:-latest}
    # No entrypoint here: the image's own entrypoint precompiles GenVM for the
    # host CPU on the first start, then runs `genlayernode run`. The keystore
    # password is NOT on a command line. It reaches the node as
    # GENLAYERNODE_PASSWORD (environment below), which the run command reads in
    # place of --password. A command-line argument is visible in process
    # listings on the host; an environment variable is not.
    container_name: genlayer-node
    restart: unless-stopped
    env_file:
      - path: ./.env
        required: false
    environment:
      # No default: this is the password that encrypts the validator's signing
      # key, and a default shared by every operator who forgot to set one is a
      # key anyone can open (the release binary carries none either). The node
      # itself refuses validator mode with an empty password ("password is
      # required for validator mode"); a full node needs none. Not a ":?" guard:
      # Compose interpolates every service, also under another profile, so a
      # guard here would stop `docker compose up -d webdriver-container` (the
      # binary install path) and a full node, which never read it.
      GENLAYERNODE_PASSWORD: "${NODE_PASSWORD:-}"
      # WebDriver metrics collector reaches Docker via the read-only proxy
      # (see docker-socket-proxy above), never the host socket directly.
      DOCKER_HOST: tcp://docker-socket-proxy:2375
    ports:
      - "${NODE_RPC_PORT:-9151}:9151"
      - "${NODE_OPS_PORT:-9153}:9153"
    volumes:
      - ${NODE_CONFIG_PATH:-./configs/node/config.yaml}:/app/configs/node/config.yaml:ro
      # The trusted protocol manifest of the network; consensus.manifestpath names this path.
      - ${NODE_MANIFEST_PATH:-./configs/node/protocol-manifest.json}:/app/configs/node/protocol-manifest.json:ro
      - ${NODE_DATA_PATH:-./data}:/app/data
      # opt/genvm/current links to the image's GenVM tree, so no version variable is needed.
      - ./genvm-module-web-docker.yaml:/app/opt/genvm/current/config/genvm-module-web.yaml
    security_opt:
      - no-new-privileges:true
    cap_drop:
      - ALL
    logging:
      driver: "json-file"
      options:
        max-size: "100m"
        max-file: "3"
        compress: "true"
    depends_on:
      - webdriver-container
      - docker-socket-proxy
    profiles:
      - node

```

2. Keep `genvm-module-web-docker.yaml` next to your `docker-compose.yaml`.

This is the release package's `.env.example`: copy it to `.env` next to `docker-compose.yaml`. The release package also ships `docker-compose.yaml` and `genvm-module-web-docker.yaml`. Set at least:

- `NODE_PASSWORD`: the keystore password, with no default. In v0.6.0-rc.1 every `docker compose` command fails while it is empty, also for a full node or the WebDriver alone. A validator sets the operator key's password (the export passphrase); a full node sets any non-empty value.
- `GENVM_VERSION=v0.6.0-rc10`: the GenVM version v0.6.0-rc.1 ships. The compose file uses it to mount `genvm-module-web-docker.yaml`; `.env.example` does not list it.
- `COMPOSE_PROJECT_NAME=genlayer-node`: the v0.6.0-rc.1 compose file has no fixed project name, so Compose names the project after the directory. With a fixed name, a new version run from a new directory replaces the old containers instead of failing with "container name ... already in use". Passing `-p genlayer-node` to every `docker compose` command does the same.
- `NODE_VERSION`: pin the exact version approved for Bradbury Phase 2, today `NODE_VERSION=v0.6.0-rc.1`. The `latest` image can belong to an older release family.
- the API key of at least one LLM provider.
- `GENLAYERNODE_ROLLUP_GENLAYERCHAINRPCKEY`, when your chain RPC provider needs a key (the Bradbury WebSocket does).

4. Import the operator key

   Install the encrypted CLI operator export into the node's keystore directory.
   The example uses the default data mount and `datadir: ./data/node`. Adapt it if
   you changed `NODE_DATA_PATH` or the configured keystore path.

   ```bash copy
   sudo install -d -m 700 -o 10001 -g 10001 ./data/node/keystore
   test ! -e ./data/node/keystore/operator.json || exit 1
   sudo install -m 600 -o 10001 -g 10001 /path/to/operator-keystore.json \
     ./data/node/keystore/operator.json
   ```

   Set `NODE_PASSWORD` in the private `.env` to the export's passphrase. This keeps
   the original encryption and avoids passing a password or private key in process
   arguments. `config.yaml` is mounted read-only: set the public registered
   operator address in the host configuration, then verify it with doctor:

   ```yaml
   node:
     operatorAddress: "0x..."
   ```

5. Checking Your Configuration

Before the first start, run `doctor` in the node container, with the same config, manifest, environment and network as the node:

```sh copy
docker compose --profile node run --rm --entrypoint /app/bin/genlayernode genlayer-node doctor
```

6. Start the services using Docker Compose:

```sh copy
docker compose --profile node up -d
```

### Telemetry

For a quick setup using Docker Compose:

1. **Set the monitoring variables in your `.env` file.** The `.env` example above lists them: the six `CENTRAL_*` endpoint and credential values, `NODE_ID` and `VALIDATOR_NAME`. All six `CENTRAL_*` values are required: Alloy stops with a message when one is missing. Get the endpoints and credentials from the Foundation team, and see the [Monitoring Guide](/validators/monitoring) for the values to use.

2. **Run docker compose**:
   ```bash copy
   docker compose --profile monitoring up -d
   ```

3. **Verify your node is pushing metrics** by checking the [GenLayer Foundation public dashboard](https://genlayerfoundation.grafana.net/public-dashboards/66a372d856ea44e78cf9ac21a344f792)

For detailed monitoring setup including Prometheus metrics, Grafana dashboards, and centralized logging with Alloy, see the [Monitoring Guide](/validators/monitoring).
